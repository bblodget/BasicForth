# x86-64 registers and machine code

What you are looking at when `dis` prints a listing. BasicForth compiles
straight to machine code, so a definition is not a thread of tokens to be
decoded — it is x86-64, and `objdump` will show you every byte of it. The
vocabulary is small: four reserved registers, and about six instruction
shapes the compiler ever emits.

This is the reading guide, not an assembler tutorial. For the instruction
set itself see `docs/x86_Quick_Reference.md` in the source tree, and
`help dis` for the disassembler's own behaviour.

At a glance:

    %r15   DSP      data stack pointer — the top item is (%r15)
    %r13   HERE     next free byte of dictionary space
    %r12   LATEST   most recent dictionary entry
    %rsp   return stack — the hardware stack, used as Forth's

    (%r15)     top of stack          8(%r15)   second item
    sub $0x8,%r15   then a store     push
    add $0x8,%r15   after a load     pop
    call <addr>  \ name              a Forth word
    ret                              end of definition

The sections — each of these is `help <topic>`:

    x86-order       which operand is the destination (AT&T puts it last)
    x86-memory      what the parentheses mean, and the lea exception
    x86-reserved    the four registers holding engine state
    x86-regs        the whole register file, and what each one is for
    x86-stack       push, pop and top-of-stack as instruction shapes
    x86-literal     numbers, strings, and data embedded in the code
    x86-calls       calling a word, control flow, and `does>` patching
    x86-abi         the C and syscall conventions, for FFI and platform code
    x86-worked      a whole definition read end to end
    x86-see-also    related pages

## x86-order

**AT&T syntax puts the destination last:** `mov src, dst`. Read it as
English — `mov %rax,%rbx` is "move rax *to* rbx". ARM64 does the exact
opposite, destination first, which is what makes switching between the two
disorienting.

Rather than memorise it, let the listing tell you. **A `$` marks an
immediate, and an immediate can never be a destination**, so any instruction
with one is self-labelling:

    sub  $0x8,%r15         # $0x8 must be the source — so %r15 is the dest
    movq $0x3,(%r15)       # ...so this stores 3 into the cell

    mov  (%r15),%rax       # no $, but the same order: dest on the right
    mov  %rax,(%r15)       # ...and this one writes

In BasicForth's own idioms that reduces to a single habit: **`%r15` on the
right means you are reading the stack; `(%r15)` on the right means you are
writing it.**

Order only changes the *meaning* for the non-commutative instructions, and
those are the two worth being careful about:

    sub $0x8,%r15          # r15 = r15 - 8, not 8 - r15
    cmp %rax,%rdx          # computes rdx - rax

That `cmp` is the classic trap. `cmp %rax,%rdx` followed by `jg` jumps when
**%rdx** is greater — the operand you read first is the right-hand side of
the comparison. BasicForth's `do`/`loop` compares with `je`, which is
symmetric, so nothing there depends on getting it right; a hand-written
`jg` very much does.

x86 assembly comes in two notations. **AT&T** puts the destination last and
marks registers with `%` and immediates with `$`; **Intel** puts the
destination first and uses neither sigil. They describe the same machine —
Intel's `mov rax, [r15]` and AT&T's `mov (%r15),%rax` assemble to the same
three bytes.

Everything here is AT&T, because GNU `as` defaults to it and that is what
`core.s` is written in — and `objdump` defaults to it too, so a `dis`
listing and the source read the same way.

## x86-memory

**Parentheses mean "the memory at".** They are the dereference, and the
closest thing in Forth is `@`:

    %r15          the address itself       ( DSP )
    (%r15)        what is stored there     ( DSP @ )

The general form has four parts, all optional, which is why it appears in
so many shapes:

    disp(base, index, scale)   →   address = base + index*scale + disp

| AT&T            | Intel         | Address                |
|-----------------|---------------|------------------------|
| `(%r15)`          | `[r15]`         | `%r15` — top of stack    |
| `0x8(%r15)`       | `[r15+8]`       | `%r15 + 8` — second item |
| `-8(%r15,%rax,8)` | `[r15+rax*8-8]` | `%r15 + %rax*8 - 8`      |

The third form is how the FFI reaches its arguments:

    mov -8(%r15,%rax,8), %rdi   # arg1

`%r15` is DSP and `%rax` is the argument count, so this indexes the data
stack **by cell rather than by byte** — the scale is 8 because a cell is 8
bytes. Scale may only be 1, 2, 4 or 8, which is exactly the set of useful
element sizes.

**`lea` is the exception: parentheses, but no memory access.** It computes
the address and stops.

    lea (%r15,%rax,8), %r15     # pop all the args

That is `r15 += rax*8` in one instruction, and nothing is read or written.
Using the address unit as an adder is a standard trick, so `lea` in a
listing is usually arithmetic rather than a pointer.

**Not every memory operand has parentheses**, which is the part that
catches people. A segment-prefixed address has none:

    mov %fs:sp0@tpoff, %rax     # loads from thread-local storage

And a bare symbol is a memory operand too — the `$` is what makes it a
value:

    mov source_addr(%rip), %rsi   # RSI = the contents of source_addr
    mov $bye_len, %rdx            # RDX = the address / immediate itself

Finally, do not confuse parentheses with `*`, which marks an indirect
branch:

    call *%rbx      # call the address IN %rbx  -- how the FFI calls C
    call *(%rbx)    # call the address STORED AT %rbx

## x86-reserved

Four registers carry engine state, and they hold it across every call:

| Register | Holds                       | Notes                              |
|----------|-----------------------------|------------------------------------|
| `%r15`     | DSP, the data stack pointer | Points **at** the top item             |
| `%r13`     | HERE, dictionary free space | Where the next compiled byte lands |
| `%r12`     | LATEST, newest dict entry   | Head of the chain `find` walks       |
| `%rsp`     | The return stack            | The machine stack, used as Forth's |

All four are **callee-saved** in the System V ABI, and that is the whole
reason they were chosen. A C function reached through the FFI — an SDL
call, `dlopen`, anything — is obliged to give them back untouched, so the
Forth engine survives arbitrary foreign code without saving and restoring
state around every call.

The corollary matters if you write inline machine code: **clobber one of
these and you corrupt the interpreter**, usually not at the instruction
that did it. If your word needs a register, use a scratch one, or save and
restore the callee-saved register you borrow.

**Everything else is scratch.** `%rax`, `%rcx`, `%rdx`, `%rsi`, `%rdi` and
`%r8`–`%r11` are caller-saved and used freely. `%rbx`, `%rbp` and `%r14` are
callee-saved but *not* reserved: primitives that want them push and pop them
first — `%rbx` is borrowed that way at 39 sites in `core.s`. Seeing `%rbx`
in a listing tells you nothing about engine state; seeing `%r15` tells you
everything.

## x86-regs

The whole register file, and what each one means here. x86-64 has sixteen
general-purpose registers; BasicForth reserves four and treats the rest as
scratch.

| Register     | 32/16/8-bit views | Role in BasicForth                      |
|--------------|-------------------|-----------------------------------------|
| `%rax`         | `%eax` `%ax` `%al`      | Scratch. C return value                 |
| `%rbx`         | `%ebx` `%bx` `%bl`      | Callee-saved scratch — push before use  |
| `%rcx`         | `%ecx` `%cx` `%cl`      | Scratch. 4th C argument                 |
| `%rdx`         | `%edx` `%dx` `%dl`      | Scratch. 3rd C arg; `mul`/`div` half        |
| `%rsi`         | `%esi` `%si` `%sil`     | Scratch. 2nd C argument                 |
| `%rdi`         | `%edi` `%di` `%dil`     | Scratch. 1st C argument                 |
| `%rbp`         | `%ebp` `%bp` `%bpl`     | Callee-saved scratch — no frame pointer |
| `%rsp`         | —                 | **Reserved: the return stack**              |
| `%r8`–`%r11`     | `%r8d` …            | Scratch. C args 5–6; `%r10` = syscall 4   |
| `%r12`         | `%r12d` …           | **Reserved: LATEST**                        |
| `%r13`         | `%r13d` …           | **Reserved: HERE**                          |
| `%r14`         | `%r14d` …           | Callee-saved scratch — not reserved     |
| `%r15`         | `%r15d` …           | **Reserved: DSP**                           |
| `%xmm0`–`%xmm15` | —                 | Floating point — see below              |
| `%rip`         | —                 | Instruction pointer; only as `sym(%rip)`  |
| `%rflags`      | —                 | Flags, set by `cmp`/`test`/arithmetic       |

The FFI is the only thing here that uses the floating-point bank: float
arguments go in `%xmm0`–`%xmm7`, a float return comes back in `%xmm0`, and
they are counted in their own sequence — the *n*th float takes `%xmm(n-1)`
regardless of how many integer arguments sit beside it.

The views are the same physical register, not separate ones — writing
`%eax` **zeroes** the top half of `%rax`, while writing `%ax` or `%al`
leaves it alone. That asymmetry is a classic source of stale high bits.

Two registers are less general than they look. `%rdx` is written implicitly
by `mul` and `div`, so it cannot be assumed to survive them. And **a
variable shift count must be in `%cl`** — `shl %cl,(%r15)` is legal,
`shl %rax,(%r15)` is not; encoding one gets you a silently different
instruction, which has cost us a real defect before.

## x86-stack

The data stack is a plain array of 8-byte cells that grows **downward**,
with `%r15` pointing at the top item. There is no top-of-stack register:
every operation goes through memory. That costs a little speed and buys a
great deal of simplicity, because no primitive has to agree with any other
about what is cached where.

So the idioms are short and completely regular:

    mov (%r15),%rax            # read top of stack (does not pop)
    mov 0x8(%r15),%rcx         # read second item
    mov 0x10(%r15),%rdx        # read third

    sub $0x8,%r15              # push: make room...
    mov %rax,(%r15)            #       ...then store

    mov (%r15),%rax            # pop: read...
    add $0x8,%r15              #      ...then release

Once you can see `sub $0x8,%r15` as the word "push", most listings read
themselves. Here is `swap`, which never moves the pointer at all:

    mov (%r15),%rax            # rax = top
    mov 0x8(%r15),%rcx         # rcx = second
    mov %rcx,(%r15)            # top = second
    mov %rax,0x8(%r15)         # second = top

**Why `drop` loads a value it never uses.** `dis drop` shows this:

    mov (%r15),%rax
    add $0x8,%r15
    ret

The load looks dead, and it isn't. The stack is bracketed by two `PROT_NONE`
guard pages, so overflow and underflow arrive as a SIGSEGV the handler turns
into a Forth error. But *moving* a pointer never faults — only touching
memory does. Without that read, `drop` on an empty stack would walk `%r15`
quietly into the guard page and the fault would surface later, inside some
unrelated word. Touching the cell first makes the error land on the word
that caused it. The same read appears at the top of every primitive that
pops.

## x86-literal

A number compiles to an **immediate** — the value is built into the
instruction, with no call and no inline data:

    sub $0x8,%r15
    movq $0x3,(%r15)           # 3

`[char] A` looks identical with `$0x41`, because by compile time it *is*
just a number. That is the common case and it needs no annotation: the
value is legible in the instruction.

The older shape — a `call lit` followed by an 8-byte cell — survives only
where the cell is **storage** that something reads or patches later: a
`constant`, a `value`, a `create` body, a deferred word, and `[']`. `dis`
knows the shape and prints the cell as data rather than decoding it as
instructions:

    call   0x40233a  \ lit
    2a 00 00 00 00 00 00 00      \ literal: 42

Strings are the other embedded shape — a call to the string runtime, an
8-byte length, then the characters:

    call   0x404ae8  \ (s")
    02 00 00 00 00 00 00 00 68 69   \ s" hi"
    call   0x404acb  \ type

Both matter for reading listings because a linear disassembler decodes
inline data as garbage instructions, and on x86 the variable-width decode
can lose step and swallow the real instructions that follow. `dis` splits
code from data before it ever calls `objdump`, which is why the listing
stays honest.

## x86-calls

Under Subroutine Threaded Code, calling a Forth word is calling a
subroutine. There is no inner interpreter and no dispatch loop:

    call   0x401844  \ dup

The `\ dup` is `dis` reverse-mapping the target through the dictionary —
`objdump` supplies the address, BasicForth supplies the name.

**A colon definition has no prologue.** It starts with its first real
instruction and ends with `ret`; `call` pushed the return address and `ret`
pops it. (ARM64 cannot do this — see `help arm64-frame` — which is the
single biggest difference between the two listings.)

Control flow compiles to ordinary branches over the same stack idioms.
`if` pops a flag and tests it:

    mov (%r15),%rax            # pop the flag
    add $0x8,%r15
    test %rax,%rax
    je   0x44f1a1              # ...to the else branch

`do`/`loop` keeps the limit and index on the return stack, which is why
`i` reads through `%rsp`:

    push %rdx                  # limit
    push %rax                  # index
    mov (%rsp),%rax            # i
    ...
    inc  %rax
    cmp  %rax,%rdx
    je   0x44f2e1              # done

Locals reach their frame through a TLS slot, so they are per-thread:

    mov %fs:0xffffffffffffffe0,%rax    # this thread's locals pointer

One instruction to find the frame, then an ordinary offset load. That is
worth noticing because ARM64 needs four instructions for the same step.

**Bytes after `ret` are not always code.** `dis` on a `create`d word shows
four `nop`s past the `ret`:

    call   0x40233a  \ lit
    08 f2 44 00 00 00 00 00      \ literal: 0x44f208
    ret
    nop
    nop
    nop
    nop

They are a patch slot. `ret` is one byte and a `jmp rel32` is five, so
`create` reserves exactly four spare bytes for a later `does>` to overwrite
the `ret` in place. Attach a `does>` and the tail becomes:

    jmp    0x44f18c

## x86-abi

Everything above concerns Forth code calling Forth code. Two other calling
conventions show up in listings — in `dis` of a platform word, and any time
you read FFI or inline assembly.

**System V AMD64, for C calls:**

| Category            | Registers                              |
|---------------------|----------------------------------------|
| Arguments, in order | `%rdi`, `%rsi`, `%rdx`, `%rcx`, `%r8`, `%r9`       |
| Return value        | `%rax` (`%rdx` too, for 128-bit)           |
| Caller-saved        | `%rax`, `%rcx`, `%rdx`, `%rsi`, `%rdi`, `%r8`–`%r11` |
| Callee-saved        | `%rbx`, `%rbp`, `%r12`–`%r15`                  |

`%rsp` must be 16-byte aligned at the `call`. Forth's return stack is
deliberately *not* ABI-aligned, so a C call cannot simply be made from
Forth code — see `docs/Core_Primitives.md` for how the boundary is crossed.

**Linux syscalls**, which the platform layer uses instead of libc:

|                |                                  |
|----------------|----------------------------------|
| Syscall number | `%rax`                             |
| Arguments      | `%rdi`, `%rsi`, `%rdx`, `%r10`, `%r8`, `%r9` |
| Instruction    | `syscall`                          |
| Return         | `%rax`, negative for `-errno`        |

Note `%r10` where the C convention has `%rcx`: the `syscall` instruction
destroys `%rcx` and `%r11`, so the kernel takes its fourth argument
elsewhere. A listing that sets up `%r10` is making a syscall, not a C call.

## x86-worked

A whole definition, end to end:

    > : sq dup 3 * + ;
    > dis sq
    sq: 27 bytes at 0044F17C (dictionary)
      44f17c:  e8 c3 26 fb ff        call   0x401844  \ dup
      44f181:  49 83 ef 08           sub    $0x8,%r15
      44f185:  49 c7 07 03 00 00 00  movq   $0x3,(%r15)
      44f18c:  e8 9e 27 fb ff        call   0x40192f  \ *
      44f191:  e8 7f 27 fb ff        call   0x401915  \ +
      44f196:  c3                    ret

Line by line: call `dup`; push the literal 3 in the two-instruction idiom;
call `*`; call `+`; return. Five source words, five pieces of machine code,
in order, with nothing in between. That is what Subroutine Threaded Code
buys — and why `dis` output is worth reading rather than trusting.

The header line tells you which of the two worlds you are in. `(dictionary)`
means the code lives in the RWX dictionary mapping, compiled at runtime.
The other case is a primitive, which lives in the binary's `.text` and comes
with a real symbol:

    > dis dup
    dup: primitive at 00401844 (in the binary)
    0000000000401844 <forth_dup>:
      401844:  49 8b 07     mov    (%r15),%rax
      401847:  49 83 ef 08  sub    $0x8,%r15
      40184b:  49 89 07     mov    %rax,(%r15)
      40184e:  c3           ret

Read TOS, make room, store it back. `dup` is three instructions.
